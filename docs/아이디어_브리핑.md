## 3. 확정 후보 10건 (씨앗 13개 → 압축)

두 갈래: **(가) 개선** = 확인된 문제를 고치자(5건), **(나) 활용** = 이 데이터로 뭘 만들자(5건).
아래는 **아이디어명 + 한 줄 요지 + 쓸 근거**까지만. 「현황/문제/제안/기대효과」 본문은 본인이 쓴다.

### (가) 개선 아이디어 5건

| # | 아이디어명 | 한 줄 요지 | 쓸 근거 |
|---|---|---|---|
| 1 | 자동차부탄 **제품코드 K015/K105 일원화** | 같은 제품이 API마다 다른 코드로 응답해 호출부가 갈라진다. 코드를 하나로 정하고 변경이력을 가이드에 명시하자 | K105는 p8·p9·p22·p23, 나머지 9개 API는 K015 / p2 변경내역 2020.03.13 제외 → 2024.09.23 추가 |
| 2 | 개방 CSV **인코딩 UTF-8 통일** | 같은 기관 개방파일이 CP949와 UTF-8로 갈려 한 번에 읽으면 한글이 깨진다 | CP949 67 / UTF-8(BOM) 6. **직접 변환·검증 73/73 통과** → `evidence/encoding_convert_20260919.md` |
| 3 | API 가이드 **표기 정합성 점검 체계** | 엔드포인트 대소문자·항목명·상표코드 집합이 문서 안에서 어긋난다. 배포 전 자동 대조를 넣자 | p22 `datepollAvgRecentPrice.do` vs 예시 `datePollAvgRecentPrice.do` / p2 `GOOD_YN5` vs p13 `GOOD_YN_5` / SKG·E1G가 p8·p22 계열에만 |
| 4 | **회차·버전 표기 규칙** 도입 | 회차별 파일이 목록 1건에 묶여 있어 "몇 건을 받았는지"가 집계 기준마다 달라진다 | 「국내석유제품 가격 동향」 1건 = PDF 3개. **우리도 이것 때문에 8건 부족으로 잘못 셌다**(실제 10건) |
| 5 | 개방 파일명 **정규화·명명 규칙 명시** | 한글 파일명이 자모 분리(NFD)되면 윈도우·깃허브에서 깨진다. 개방 단계 규칙을 문서화하자 | ⚠ **근거 재확인 필요** — 아래 주석 참조 |

> ⚠ **5번 주의**: 우리가 받은 78개가 전부 NFD였던 것은 **맥에서 내려받아 생겼을 가능성이 크다**
> (서버 문제라면 오피넷·공공데이터포털 두 곳에서 똑같이 나올 이유가 없다).
> 파일명에 붙은 `(1)` 4건도 브라우저가 붙인 것이지 개방 데이터의 중복이 아니다.
> 제출하려면 **다운로드 응답의 `Content-Disposition` 파일명 인코딩을 직접 확인**해 근거를 바꿔야 한다.
> 확인 전까지는 5번을 예비로 두고 아래 예비 후보와 바꾸는 편이 안전하다.

## 4. 작성 틀 — 아이디어 1건당 (실적 제출 양식)

각 아이디어를 아래 4단으로 쓴다. **문장은 반드시 본인이 검증 후 직접 작성.**

```
■ 아이디어명:

1) 현황   — 지금 데이터/서비스가 어떤 상태인가 (숫자·근거 포함)
2) 문제   — 그래서 무엇이 불편/비효율/오류인가
3) 제안   — 구체적으로 무엇을 어떻게 바꾸/만들자
4) 기대효과 — 누구에게 어떤 가치가 생기나 (가능하면 정량)
```

**작성 팁**
- "현황·문제"는 위 2번 표의 수치·근거를 그대로 인용하면 설득력이 생긴다.
- 활용 아이디어는 "어떤 데이터셋 + 어떤 데이터셋"을 결합하는지 명시하면 구체적이 된다.
- AI에게는 *구조 잡기·후보 확장·표현 다듬기*까지만 맡기고, 최종 판단·문장은 본인이.
